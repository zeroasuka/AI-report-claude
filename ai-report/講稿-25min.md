## 【P4 · 打字 vs 說話】　⏱ 50s

先問一個問題：**為什麼我們到現在，還要用十根手指，去追趕自己的思考？**

看這兩個數字——打字平均每分鐘 45 個字，說話可以到 220 個字，差不多五倍。而 AI 一秒鐘就讀完一千個字。

所以問題來了：當對面這個 AI 讀得這麼快、你講得又比打得快五倍——**那你為什麼還在打字？** 這就是這套方法的第一塊基石：把輸入，從手指換成嘴巴。

## 【P5 · Typeless 按住就講】　⏱ 50s

我用的工具叫 **Typeless**，核心就一個動作：**按住就講。** 它幫你解決三件事：

1. **想法不用等手指**——腦中想到什麼直接說，不用先在心裡整理成漂亮句子。
2. **口語也能變指令**——你可以停頓、重講、中英夾雜；AI 要的是完整上下文，不是漂亮作文。
3. **到哪裡都能用**——ChatGPT、Codex、Slack、Email、文件，只要能打字的地方就能用語音驅動。

而且 macOS、Windows、iOS 介面一致，學一次到處用。右邊就是實際截圖——不管電腦還是手機，都是「按住 → 說 → 貼上」。

## 【P7 · 從聊天，到執行】　⏱ 70s

接下來是觀念上最重要的一頁。**90% 的人用 AI，是把它當聊天室——一問一答。**

看左邊：「寫個 app」→ AI 問「什麼 app？」→「查料件的」→「什麼語言？什麼資料庫？」→ 最後你「算了」。為什麼會這樣？因為你上下文沒包好，被它反覆反問，而且講完還要自己複製貼上去跑。

進階用法在右邊：**先寫一份規格書，再交給 Agent 工具去執行。**

第一步，在聊天視窗——用 Gemini、ChatGPT、Claude.ai——把需求討論清楚，產出一份 Markdown 規格書。第二步，把規格書貼給 Claude Code、Cursor、Codex，**它自己改檔、自己跑指令、自己生網站、自己部署**。

一次跑完，直接給你能用的成品。這就是「聊天室」跟「執行助理」的差別。

---

## 【P8 · 想→寫→做】　⏱ 50s（精簡）

把這個概念整理成一條工作流，就三個字：**想、寫、做。**

- **想**——在聊天視窗跟 AI 討論，逼它反問你、補你沒想到的細節。這步在便宜的聊天視窗做，省 token。
- **寫**——產出一份 Markdown 規格書：角色、目標、限制、範例、驗收條件，變成 AI 的「需求單」。
- **做**——把規格書貼給 Agent，它就去改檔、跑指令、生 App、部署上線。

一句話：**先想清楚，再交給 Agent 做。**

## 【P10 · Model ≠ Agent】　⏱ 65s（核心）

這頁是整場最重要的觀念：**Model 是 Model，Agent 是 Agent。** 你不是在跟一個聊天機器人講話，而是**驅動一個 Agent**。

中間這顆是「腦」——也就是 Model，GPT-5、Claude、Gemini、DeepSeek 這些都是。Model 只會做一件事：**想**。它會推理、會答題、會產生文字——但它不會動手，只活在對話框裡。換一個 Model，等於換一顆腦。

而 **Agent = Model + 動手能力**。它會讀檔、改檔、跑指令、調工具，有權限邊界、有交付產物。Codex、Claude Code、OpenClaw 都是 Agent。換工具只是換包裝，裡面的模組是一樣的。

記住這一句就好：**Model 會想，Agent 會做。**

---

## 【P11 · 6 種核心模組】　⏱ 20s　⏩ 一句帶過

Skill、MCP、AGENTS.md 這些名詞到底是什麼？它們不是並列的功能，而是 Agent 圍繞 Model 的**六種核心模組**——Prompt（任務指令）、Skill（專業領域包）、Markdown（文件）、AGENTS.md（專案規範）、Memory（長期記憶）、MCP（對外連接）。一句話：**它們都是在幫 AI 建立上下文（Context），讓它知道要做什麼、怎麼做、記住什麼、從哪裡取資料。** 細節留給線上版。

---

## 【P12 · 4 種介面】　⏱ 15s　⏩ 一句帶過

同一個 Codex 有四個入口——手機、桌面、CLI、IDE 外掛。選的不是介面，是**工作方式**：手機遠端控制、桌面長時間開發、CLI 自動化、IDE 邊寫邊交辦。一句話：**換的是入口，不是能力。** 這頁我跳過。

## 【P13 · 五層工作流】　⏱ 45s（精簡）

把前面六種模組串起來，就是**用五個問題重新理解 Codex**——任何 Agent 工具都跑這條五層鏈路：

**入口**——從哪裡發任務？**執行環境**——在哪裡幹活？**上下文**——憑什麼做對？**權限邊界**——有什麼邊界？**交付**——最後交付什麼結果？

所有 Agent 工具，不管名字多炫，骨架都是這五步。

## 【P15 · Case01 · Part Number 痛點】　⏱ 50s

第一個案例，從我每天的工作講起。Part Number 散落在文件和 Email 裡，我的痛點是三件事：第一，**PN 散在各處要先找到**；第二，**找到要丟進公司內部系統查料、出料**；第三，**還要整理出料的物流資訊**——收件人、時間、地址、電話、備註。

這個小工具不是要取代公司系統，而是把散落的 PN 先匯入、搜尋、複製，再快速貼回內部系統。老實說**這件事我以前覺得「沒辦法」**——我不是工程師，不會 React、不會後端、不會部署。我以為這種工具輪不到我自己做。

## 【P19 · Case02 · Gemini→規格書→Codex】　⏱ 70s（核心）

這頁是整套方法最完整的示範，**兩個 AI 接力。**

- **第一步**，我先跟 Gemini 聊。我說我五月要去成都八天、四個城市，想做一個手機旅遊 App，可以編輯行程、看地圖、記帳，請它幫我寫一份詳細到 Codex 能直接照做的規格書。Gemini 反問我五個關鍵問題——行程要不要可編輯、幾個城市怎麼切換、預算分幾類要不要分帳、資料存本地還是雲端、UI 風格——我一一回答。
- **第二步**，Gemini 產出一份兩千五百字的 Markdown 規格書，詳細到工程師看著就能做。
- **第三步**，我把整份規格書貼給 Codex，它就照著生出單檔 HTML、套熊貓主題、加 localStorage。

為什麼要分兩個 AI？因為**規格書在便宜的聊天視窗寫好，省 token；真正吃 token 的寫程式工作，才丟給 Agent**。先把需求聊清楚，再交給 Agent 執行，大幅減少來回修改。
